## Модель данных

`user_id` используется в качестве partition key, поскольку благодаря этому запрос ленты по
пользователю обращается к одной партиции без сканирования
остальных пользователей. `event_time` используется в качестве clustering key, чтобы события внутри
партиции упорядочены по
убыванию времени, поэтому `LIMIT` возвращает последние события без сортировки на клиенте

## Вставка и чтение

`insert_events` готовит INSERT один раз на вызов, затем для каждого события создаёт BoundStatement,
задаёт `bound.consistency_level` и выполняет запрос. Время события —
`2026-01-01T00:00:00Z + i минут`, типы циклически чередуются, payload создаётся через
`json.dumps({'seq': i})`.

`read_last` использует подготовленный SELECT с условиями
`WHERE user_id = ? ORDER BY event_time DESC LIMIT ?` и возвращает список строк драйвера. Значения
передаются через bind-параметры. Имя таблицы выбирается из разрешённых двух имён, поскольку
идентификаторы CQL нельзя подставлять через `?`.

PreparedStatement позволяет повторно использовать разобранный сервером запрос и передавать параметры
отдельно, уменьшая повторный разбор CQL и объём передаваемого текста.

| Что вставлено                            | Количество | Суммарное время, с | Среднее на запись, мс |
|------------------------------------------|-----------:|-------------------:|----------------------:|
| События пользователя 1001 в user_actions |     10 000 |              7,497 |                0,7497 |

## Консистентность ONE и QUORUM

Сценарий записывает по 1000 событий для пользователей 2001 и 2002 и читает по 20 последних событий.
Консистентность задаётся на каждом BoundStatement, настройки общей сессии не меняются.

| Уровень | Запись, мс | Чтение, мс |
|---------|-----------:|-----------:|
| ONE     |        609 |          5 |
| QUORUM  |        725 |          3 |

`N` — число реплик данных, здесь 3; `W` — число подтверждений записи, `R` — число ответов чтения.
Условие `W + R > N` обеспечивает пересечение наборов реплик. ONE ждёт один ответ, QUORUM при RF=3 —
два. Запись направляется всем репликам, уровень определяет необходимое число подтверждений. При
чтении QUORUM версии согласуются по ответам реплик. Для ONE/ONE сумма равна 2, пересечение не
гарантировано, для QUORUM/QUORUM — 4, пересечение гарантировано. Поэтому последующее quorum чтение
видит подтверждённую quorum запись при отсутствии конфликтующих конкурентных изменений. Сочетание
ONE и QUORUM даёт ровно 3, поэтому строгого неравенства нет

Для ленты аудита я выбрал бы QUORUM и для записи, и для чтения, т.к нам важно видеть подтверждённое
действие
сразу. При RF=3 допустим отказ одной реплики, при доступности только одной запросы не выполнятся.
Цена в данном случае это ожидание дополнительных ответов.

## Сжатие SSTable

| Таблица                        | Space used (total), байт | SSTable count | SSTable Compression Ratio |
|--------------------------------|-------------------------:|--------------:|--------------------------:|
| user_actions (LZ4)             |                   34 032 |             1 |                   0,39372 |
| user_actions_none (без сжатия) |                   78 274 |             1 |                  -1,00000 |

LZ4 сократил полный занимаемый объём на `1 − 34 032 / 78 274 = 56,52%`, примерно в 2,30 раза.

Сжатие требует CPU при записи SSTable во время flush/compaction и при распаковке блоков чтения, а
также памяти под метаданные. Взамен уменьшаются занимаемое место и дисковый ввод-вывод.
Повторяющиеся типы событий и структура JSON делают его полезным для данного набора.

## Bloom-фильтр

| Показатель                   | Значение |
|------------------------------|---------:|
| Bloom filter false positives |        0 |
| Bloom filter false ratio     |  0,00000 |

Bloom-фильтр проверяет наличие partition key в конкретной SSTable. Отрицательный ответ означает, что
партиции в этом файле точно нет, поэтому поиск данных в нём можно пропустить. Положительный ответ
означает
только возможное наличие и требует дальнейшей проверки. Ложноположительное срабатывание вызывает
лишний поиск.

`false positives` — число ложных положительных ответов, `false ratio` — их наблюдаемая доля среди
положительных ответов фильтра.

Фильтр полезен при поиске ключей, отсутствующих во многих SSTable. Его вклад мал при полном
сканировании, редких чтениях или чтении данных из memtable.

## Repair

Anti-entropy repair синхронизирует реплики вне пути пользовательского чтения через сравнение
диапазонов
данных с помощью деревьев Merkle и передаёт различия. Он нужен после длительных простоев и
пропущенных записей, когда хинтов недостаточно, а также регулярно для данных, которые редко читают.
Без него расхождения могут сохраняться и приводить к устаревшим чтениям.

Удаления распространяются как tombstones. Repair должен охватить данные до истечения
`gc_grace_seconds`, чтобы удаление дошло до реплик. Tombstones удаляются compaction при выполнении
условий очистки, отсутствие repair само по себе не запрещает такую очистку. Если маркер удалён до
синхронизации отставшей реплики, старые данные могут воскреснуть. Repair обеспечивает безопасную
сходимость, но сам не является операцией удаления tombstones.

Read repair исправляет расхождения только в данных, затронутых конкретным
чтением. Hinted handoff сохраняет пропущенные мутации для временно недоступной реплики и доставляет
их после восстановления. Оба механизма не заменяют периодический anti-entropy repair.
